## Frozen production design: implementation pending

Architecture and spike closure reviewed; production acceptance remains pending.
Static review/reference feasibility does not verify future production code.
Trusted host controls two separate Linux Docker compartments; no host SQL broker.

PROGRAM: fresh container per program, mounting only selected read-only DB and
allowlisted read-only real runtime bundle. Invoke existing
`run_ptc_program(program, db_path)`/`sql_catalog`, no gold/TaskView.
Minimal project closure: `ptc/{__init__,runtime,sql_arms,sql_runtime,sqlite_safety}.py`,
stdlib/native SQLite; provider harness stays lazy.
Hard memory 256 MiB (`268435456` bytes), zero additional swap, 10s external deadline,
cleanup ≤12s, stdout 1 MiB, stderr 64 KiB, program 65,536 UTF-8 bytes,
bounded tmpfs. No whole repository, gold, captures, credentials, Docker socket
or other host filesystem access.

Local UNIX Docker daemon/immutable local image only,
`--pull=never`. Both compartments require nonroot/read-only root, dropped
capabilities/no-new-privileges, private PID/IPC, network none, seccomp denying
sockets/fork/clone, pids=1, nofile=64 and owned cleanup. Same-PID execve/reexec
is allowed, not shell-free execution. Effective hostname is
`co-train-isolation`; exact initial ENV7, six read-only paths (including
`/dev/mqueue`) and twelve masked paths are bound.

SCORER: separate trusted compartment executes unchanged protected EX, including
prediction/gold execution, fetch, normalization and comparison. Never run PROGRAM
Python/state there. Mount only approved scorer code, selected DB and gold.
Gold exists only in controller/scorer. Hard memory 256 MiB (`268435456` bytes),
zero additional swap, 30s external whole-score deadline, 64 KiB result envelope,
64 KiB stderr, 16 MiB `/tmp`, not total writable storage.
Return only strict complete existing `ExResult`, never rows; no host
`evidence._score` fallback. Host materialization's 2,000-VM-step callbacks/
500,000-row limits are cooperative, not hard memory/byte bounds. Read-only access/
`MemoryError` is not resource isolation; no demonstrated legacy vulnerability.

256 MiB replaces our unsafe 1-GiB proposal.
Across pilot processes, allow only ONE compartment at a time.
For every launch freshly measure available memory as
`min(VM_MemAvailable, VM_total - sum(raw charged container memory))`.
